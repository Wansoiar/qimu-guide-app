# 结束游览确认与 main 整合

## 提交意图

`feat/device-provisioning` 相对 `main@4fe32d1` 只有一个独有提交：`9da9f8f`，标题为“结束游览/结束上次订单先确认后端停止，失败明确提示不误报”。该提交将结束流程从异步发送停止请求后立即清理，改为确认后端停止成功后再擦眼镜、删除本地文件和完成订单；补充确认超时、失败提示、页面进度分流和手机号输入过滤。

本次将 `main@4fe32d1` 合入 `feat/device-provisioning`，保留双方历史；尚未将功能分支合入 main。显式冲突位于 `GuideApiClient`、`RealtimeGuideManager`、`TourReturnCoordinator`、`strings.xml`。main 中已落地的 RTC 恢复/续签、退出请求隔离、前台保活、字幕分轮、生产域名限制和分享 Session 约束均保留。

## 整合后的结束流程

1. 用户确认结束，归还事务锁定眼镜及媒体目录；捕获业务 session、RTC room/task 和当前公参 Header。
2. 立即停止本地收音、RTC 引擎和拍照任务，撤销恢复、续签和待处理创建回调。保留业务订单、RTC 身份、字幕和媒体文件，不再自动开始对话。
3. 使用独立客户端请求 `/v1/rtc/session/stop`，始终携带 `end_session=true` 和已捕获的 Header。创建尚未回包、重启后缺少完整 RTC 身份时使用 session-only stop，不发送空 room/task，也不视为“没有会话可停”。
4. 只有 HTTP 成功、业务 `code=0` 且 `data.stopped` 明确为布尔值 `true`，才允许进入眼镜 reset、本地清理及完成订单。HTTP 200 但 `stopped=false`、空体、字段缺失、格式错误均不放行。后端错误原因可显示；`ok` 不作为失败提示。
5. 失败或超时释放归还占位，保留订单及媒体并提供重试结束。由于后端实际停止状态可能不明，不自动恢复麦克风或新建 Agent。活动导览在对话页显示结束重试入口，设备页保留上次订单清理告警。

## 超时、重复结果及页面状态

- 从确认开始记录单调时钟的 **20 秒绝对截止时间**。每次 HTTP call、连接、读写超时都使用当时剩余预算，让后端正常耗时 5–10 秒的停止请求能够完成；快速失败最多重试 3 次，250/500 毫秒等待也计入同一预算，不重新计时。
- UI 确认超时按同一剩余预算调度，触发后取消该确认客户端。`ReturnConfirmationGate` 保证当前操作只有一个结果能推进，并在消费成功回包时再次检查绝对截止时间；即使 UI 超时回调晚执行，截止后的成功也不能触发清理。重复回包、上一次重试回包同样失效。
- 后端确认成功后仅清理本地 RTC 状态，不重复补发停止请求。崩溃/常规异步停止路径仍使用 main 的原有 API 与身份隔离。
- 活动导览的进度、成功及失败提示由导出页处理；上次订单由设备页处理，终态仍保留流程类型用于分流。前台服务收到失败后更新通知并释放不再需要的 WakeLock。
- 保留 11 位数字手机号输入过滤；“进入导览”文案与 main 一致。
