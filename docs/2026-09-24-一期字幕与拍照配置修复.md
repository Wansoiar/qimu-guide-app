# 一期字幕与拍照配置修复（SC-02 / SC-01）

基线：`main@a40ad842e086c2e70e23dda80abe3bc9db0f2742`。工作分支：`codex/ysc-phase1-app`。

实现前设计已评审通过：同轮多句合并；新轮/重连独立；SDK/subv 双通道保留来源、补齐轮次；缺轮次采用明确的时间降级边界；照片/状态作为分隔。以下是 2026-09-24 的本地实现与验收记录，不包含真机验收结果。

## 问题与范围

旧 `DialogueFragment.upsertSubtitle` 只比较说话人，连续两轮 AI final 即使 sequence 不同仍追加进同一气泡。虽然管理器把 RTC generation 编入 sequence，UI 也未将它作为气泡边界。subv 已有 roundId，但上层回调丢失了该字段；原文本去重还会吞掉 1.5 秒内同说话人的真实重复用语。

只修字幕身份、气泡展示和移除一期场馆 `photo_enabled` 消费。没有新增 App 依赖，没有实现锁屏进程/音频保活、修改后台服务或操作设备/生产环境。

## 字幕方案

- `RtcVoiceChatManager` 回调携带来源（SDK/BINARY）、roundId 和 sequence。已核验当前缓存 RTC SDK 3.60.105.3500 的 `SubtitleMessage` 不含 roundId，SDK 事件使用未知轮次 0。subv 接受 `roundId` 和 `round_id`。
- `BinarySubtitleTracker` 维护无 sequence 的分句身份；相同轮次 interim/final 使用同一序号，已知轮次变化不会复用旧序号。完整 final 指纹用于包重放去重；完全没有轮次/序号的包只在 1.5 秒内抑制相同重放，避免永久吞掉后来重复的原句。
- `SubtitleTranscript` 为 final 建立 canonical entry；事件身份包含 RTC generation、连接边界、speaker、source、roundId、sequence。只在不同来源之间用 1.5 秒窗口匹配同文本；同来源的新 sequence、两个已知不同轮次均保留。
- SDK 先到、subv 后到且匹配时，更新同一条 entry 的 roundId，通知 UI 重算。不能在首次 SDK final 时永久固定气泡归属。
- `SubtitleTimeline` 是纯 Java 投影。实时和快照都 upsert 同一组 canonical entries；重复快照幂等。已知轮次按 generation + 连接边界 + speaker + roundId 归并。同轮多句形成一个气泡，旧轮乱序 final 更新原气泡；同来源分句按 sequence 排序，不比较两个来源的序号大小。
- 同 RTC 实例的房间中断/Agent 离房同样建立边界并重置底层字幕跟踪，新 RTC 实例继续使用既有 generation 门禁拒绝旧实例回调。
- 照片、拍照状态和本地错误是视觉分隔，后续讲解不能跳回照片上方的旧气泡。

## 降级限制

1. 没有 roundId 时，同 speaker 连续 final 在 **10 秒以内的间隔、45 秒以内的片段跨度**暂时合并。使用 `SystemClock.elapsedRealtime()`，不使用系统日期决定分段。已知 roundId 不受这两个超时拆分。两个快速连续、无用户 final、且完全没有 roundId 的真实轮次无法可靠区分，这些常量只是确定的降级规则。
2. SDK 不带轮次、两通道序号又可能不同，跨来源同事件的识别依赖相同文本和 1.5 秒窗口。超过窗口或两边文本不同不会贸然合并；可能保留重复文本，需要真机采样确认实际到达延迟。完全无身份的重复 subv 同样只能采用有界窗口。
3. metadata 补全会重算显示列表；按 final 触发，非实时逐字刷新。没有引入新的计时器或服务。
4. 新建 Fragment 的快照恢复覆盖字幕；照片/拍照状态仍保持现有 Fragment 内存生命周期，没有新增媒体持久化。进程被杀后的恢复、锁屏后保持持续收音均未在本修复中承诺。
