## 1. 背景与目标

现有 APP 端初始化实现（`ProvisioningActivity` + `MockProvisioningApi`）与后端架构脱节，
且设备初始化信息目前不落库（全部走 Mock）。本次重做目标：

1. 运营人员通过 APP 完成「手机 + 眼镜 + 场馆」的原子绑定初始化。
2. 手机 SN 作为设备身份的**找回键**：重装 / 恢复出厂 / 重置后，输入同一 SN 即可恢复
   同一 `device_id`，不重复建设备。
3. 设备信息通过鉴权的上报接口落库，维护**手机 / 眼镜两类设备**及**当前连接状态**。
4. 支持运营人员在 APP 端一键**重置**（解除绑定），重置只解除绑定、不删设备历史。

旧版文档的核心差异（已废弃的）：
- ~~`install_id` 作为安装身份~~ → 手机只以 `phone_sn` 为身份找回键。
- ~~`provisioning_token` / `device_credential` / `handshake` 换取 device_token~~ → 直接复用
  运营后台 `admin_user` 的 JWT；设备上报与重置均用该 JWT 鉴权。
- ~~独立 `/v1/device-provisioning/*` 接口组~~ → 复用/改造现有 `/v1/admin/*` 接口。

## 2. 身份模型

| 概念 | 定义 | 说明 |
|---|---|---|
| `phone_sn` | 运营从手机设置/机身/资产标签录入的序列号，服务端标准化为 `trim + UPPERCASE` | **身份找回键**，服务端唯一索引；手机设备长期唯一 |
| `device_id`（手机） | 服务端生成的 UUID，首次初始化时创建，之后按 `phone_sn` 复用 | 对外业务主键；重装/重置后保持同一值 |
| `device_id`（眼镜） | 眼镜 BLE MAC，格式 `AA:BB:CC:DD:EE:FF`，标准化为大写 | 眼镜设备唯一标识（已确认单机稳定） |
| `venue_id` | 服务端场馆 UUID | 引用 `venue.id` |
| `admin_user` | 运营账号，所有运营共用一个账号（env 种子管理员） | 见 §4 登录 |

要点：

- **只有手机维度上报**。APP 上报手机 + 它当前连接的眼镜（MAC + 名称），服务端在同一张
  `device` 表中拆出「手机记录」和「眼镜记录」，并用 `connected_glasses_sn` /
  `connected_phone_id` 互相标记当前连接。
- **手机 SN 敏感**：属于设备资产标识，只能走 HTTPS；写入操作日志时应脱敏（见 §6.3），
  运营后台展示建议默认打码。
- **同一 SN → 同一 `device_id`**：无论 `venue_id`、连接的眼镜如何变化，只要 `phone_sn`
  不变，`device_id` 就不变。使用次数等设备维度累计数据在重绑后**保留**（见 §5）。

## 3. 总体流程

```
打开 APP
 ├─ 本地已存 device_id（已初始化）→ 进入使用页（游客免登录）
 └─ 本地无 device_id（未初始化）→ 运营登录页
        └─ 登录成功 → 初始化向导
              Step1 连接眼镜（BLE 扫描，强制必连，取 MAC）
              Step2 录入手机 SN（防呆输入）
              Step3 选择场馆（带 token 拉列表，仅 active）
              Step4 确认初始化 → POST /v1/admin/devices/report → 存 device_id → 进使用页

使用页（游客可用）
 └─ 运营入口：长按标题/Logo 3 秒 → 运营登录（token 未过期免登录）→ 重置确认
        → POST /v1/admin/devices/{device_id}/reset → 清本地 device_id → 直接进初始化向导
 └─ 调试入口（仅 debug 包）：连点标题 5 次（800ms 窗口内）→ 开启调试预览
        （免导览会话直接预览对话/导出页）

游客点「开始使用」→ 创建导览会话（携带 device_id）→ 服务端 usage_count +1
```

## 4. 接口设计

### 4.1 运营登录（复用现有）

`POST /v1/admin/auth/login` — **无鉴权**（中间件白名单保留）。

请求：
```json
{
  "username": "operator",
  "password": "********"
}
```

响应（现有实现，无需改动）：
```json
{
  "code": 0,
  "data": {
    "access_token": "<jwt>",
    "expires_in": 86400,
    "token_type": "Bearer",
    "admin": { "id": "uuid", "username": "operator", "display_name": "...", "is_super_admin": false }
  }
}
```

- Token 有效期 `jwt_expire_seconds = 86400`（24h）。
- 失败处理：统一 `invalid username or password`；10 次失败锁 30 分钟，`data.locked_seconds`
  返回剩余锁定秒数，APP 展示。
- **APP 端**：登录成功后把 `access_token` / `expires_at` / `display_name` 加密存本地
  （`OperatorSessionStore`，见 §7.3）。初始化与重置流程复用该 token；遇到 401 引导重新登录。

### 4.2 场馆列表（复用现有）

`GET /v1/admin/venues` — **需要 Bearer token**（`/v1/admin/` 下，中间件校验；不做场馆范围过滤，所有账号可见全量）。

- APP 端只取 `status=active` 的场馆，使用 `id / code / name / address`。
- 现状返回 `items / total / page / page_size` 分页结构，现有实现无需改动。

### 4.3 设备初始化 + 信息上报（改造现有 report）

`POST /v1/admin/devices/report` — **需要 Bearer token**。

> 改造点：将该路径从中间件 `SKIP_AUTH_PREFIXES` 白名单**移除**（现在是 `apps/api/middleware.py`
> 第 40 行），并要求 `Content-Type: application/json`。一次调用既是「初始化」也是「状态上报」：
> 按 `phone_sn` upsert，不存在则创建、存在则复用并更新。**不允许再新建独立初始化接口**。

请求（APP 实际上报字段）：
```json
{
  "phone_sn": "R8Y1234ABC",
  "model": "HUAWEI LYA-AL00",
  "os_version": "Android 12",
  "app_version": "1.1.1",
  "glasses_mac": "AA:BB:CC:DD:EE:FF",
  "glasses_name": "V03 眼镜",
  "venue_id": "61f1f93d-fe42-49d0-b392-bcbf9cd1c13d"
}
```

响应：
```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "device_id": "dev_uuid",
    "phone_sn": "R8Y1234ABC",
    "venue": { "id": "61f1f93d-...", "code": "NAMOC", "name": "中国美术馆" },
    "glasses": { "device_id": "AA:BB:CC:DD:EE:FF", "name": "V03 眼镜" },
    "provisioned_at": "2026-08-12T10:00:00Z"
  }
}
```

服务端必须在一个数据库事务内完成：

1. 标准化 `phone_sn`（`trim + UPPERCASE`），校验格式（见 §6.1）。
2. 按 `phone_sn` 查手机设备记录：
   - 命中 → **复用** `device_id`，更新 `model / os_version / app_version / venue_id /
     connected_glasses_sn / last_active_at`；
   - 未命中 → 新建手机记录（`device_type='phone'`，`device_id=UUID`，`phone_sn`）。
3. 按 `glasses_mac`（标准化为大写）查眼镜设备记录：
   - 命中 → 复用 `device_id`，更新 `name / venue_id / connected_phone_id / last_active_at`
     （`connected_phone_id` 存手机 `device_id`，非 SN）；
   - 未命中 → 新建眼镜记录（`device_type='glasses'`，`device_id=MAC`）。
4. 写操作日志（`device_initialize`，脱敏，见 §6.3）。
5. 返回手机 `device_id` 等。

幂等：同一 `phone_sn + glasses_mac + venue_id` 重复提交，不重复创建手机/眼镜记录，直接更新
字段即可（upsert 天然幂等）。

眼镜换绑语义：若眼镜 MAC 当前 `connected_phone_id` 指向其他手机，本次**覆盖**为新手机
（弱绑定，记录当前连接状态；历史可通过操作日志追溯）。覆盖前需校验：旧手机存在**进行中的
导览会话**（`session.status='active'` 且 `device_phone_id` 指向该手机）时返回 409，提示先
结束会话，不做覆盖；否则直接覆盖更新——换绑成功后，**旧手机记录的 `connected_glasses_sn`
同步清空**（旧手机不再连接这副眼镜），眼镜 `connected_phone_id` 更新为新手机 device_id，
新手机 `connected_glasses_sn` 指向该眼镜 MAC。

### 4.4 重置（新增）

`POST /v1/admin/devices/{device_id}/reset` — **需要 Bearer token**，写操作日志。

请求：
```json
{ "reason": "venue_reconfiguration" }
```

服务端行为（事务内）：

1. 按 `device_id` 查手机记录；不存在返回 `device_not_found`。
2. 记录旧值（旧 `venue_id`、旧 `connected_glasses_sn`）用于日志。
3. 手机记录：`venue_id = null`、`connected_glasses_sn = null`（`online_status` 不动，见 §5.2）。
4. 按旧 `connected_glasses_sn` 找到对应眼镜记录：`venue_id = null`、
   `connected_phone_id = null`。
5. **保留**手机记录的 `device_id / phone_sn / model / os_version / app_version / usage_count`
   等一切设备维度数据（下次按同一 SN 初始化时恢复同一 `device_id`，使用次数继续累计）。
6. 写操作日志（`device_reset`，含 `reason`、旧场馆、旧眼镜，操作人自动取自 token）。

响应：
```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "device_id": "dev_uuid",
    "status": "unprovisioned",
    "reset_at": "2026-08-12T11:00:00Z"
  }
}
```

幂等：对已无绑定的设备重复 reset，仍返回成功（`status=unprovisioned`）。

**APP 端**：只在收到成功响应后清除本地 `device_id` 等初始化状态并进入初始化向导；接口失败时
本地状态保持不变。

### 4.5 会话创建关联（usage_count）

> 现状脱节点：APP 的 `TourSessionApiClient` 调 `POST /sessions`，**后端不存在该路由**；后端
> 真实的会话创建是 `POST /v1/rentals/start`（PIN 鉴权）。本契约仅规定设备侧语义，具体统一到
> 哪个会话接口由后端同事在本模块落地时一并处理（见 §8）。

- 游客「开始使用」创建导览会话时，APP 传**初始化的 `device_id`**（替换当前传 `ANDROID_ID`
  的做法），后端写入 `session.device_phone_id`。
- 会话创建成功后，服务端对 `device_phone_id` 对应的手机设备记录 `usage_count = usage_count + 1`。
- `usage_count` 只由会话创建触发累加；`report`（初始化/启动上报）**不累加**。

### 5.1 `device` 表（手机 + 眼镜同一张表）

现状字段（`infrastructure/models.py:40`）与本次调整：

| 字段 | 类型 | 现状 | 调整后 | 手机 | 眼镜 | 说明 |
|---|---|---|---|---|---|---|
| `id` | UUID | ✓ | 不变 | ✓ | ✓ | 主键 |
| `device_type` | String(16) | ✓ | 不变 | phone | glasses | |

| **`phone_sn`** | String(64) unique nullable | ✗ | **新增** | ✓ | ✗ | 身份找回键，唯一索引；眼镜行为 NULL |
| `model` | String(64) | ✓ | 不变 | ✓ | ✗ | 手机型号（`MANUFACTURER + " " + MODEL`） |
| **`os_version`** | String(64) | ✗ | **新增** | ✓ | ✗ | 手机系统版本 |
| **`app_version`** | String(32) | ✗ | **新增** | ✓ | ✗ | APP 版本 |
| **`name`** | String(64) | ✗ | **新增** | ✗ | ✓ | 眼镜名称 |
| `venue_id` | UUID nullable | ✓ | 不变 | ✓ | ✓ | 当前归属场馆 |
| `connected_glasses_sn` | String(128) | ✓ | 不变 | ✓ | ✗ | 手机当前连接的眼镜 MAC |
| **`connected_phone_id`** | String(128) | ✗ | **新增** | ✗ | ✓ | 眼镜当前连接的手机 device_id（服务端 UUID，非 SN） |
| `online_status` | String(16) | ✓ | 不变 | ✓ | ✓ | online / offline，见 §5.2 |
| `usage_count` | Integer | ✓ | 不变 | ✓ | ✗ | 使用次数，会话创建时 +1，重置不归零 |
| `last_active_at` | DateTime | ✓ | 不变 | ✓ | ✓ | 最近一次上报/使用时间 |
| `created_at` / `updated_at` | DateTime | ✓ | 不变 | ✓ | ✓ | |

> 现状设备记录里 `device_id` 已有值（可能是预设值），本次对齐后手机 `device_id` 统一为
> 服务端生成的 UUID，存量数据需一次数据清洗/重建（后端同事评估）。

**推荐加唯一约束**：`UNIQUE(phone_sn)`（PostgreSQL 唯一索引允许多个 NULL，眼镜行不受影响）。
同一时刻一台手机最多绑定一副眼镜、一副眼镜最多绑定一台有效手机（当前连接语义下由 report
覆盖逻辑保证）。

### 5.2 `online_status` 语义

`online_status` 为**运营手动上线/下线状态**，仅由后台 `/v1/admin/devices/{device_id}/online` /
`/offline` 端点控制。设备初始化/上报（`report`）与重置（`reset`）**不修改**该字段；看板
"在线设备数"等统计沿用现有 `online_status` 口径，不受本模块影响。

### 5.3 `admin_operation_log` 表（复用现有）

沿用现有表结构（`infrastructure/models.py:85`），通过 `log_operation()` 写入：

| 操作 | `operation_type` | `resource_type` | `resource_id` |
|---|---|---|---|
| 初始化/上报 | `device_initialize` | `device` | 手机 `device_id` |
| 重置 | `device_reset` | `device` | 手机 `device_id` |

- `admin_user_id` 自动取自 token（中间件注入 `request.state.admin_user_id`），共用账号下日志
  记录到账号级。
- `request_params` / `response_summary` 落 `phone_sn` 时**必须脱敏**（见 §6.3）。
- `device_reset` 建议在 `request_params` 中记录 `reason`、旧 `venue_id`、旧 `glasses_mac`，
  保证可审计。

### 5.4 `session` 表（关联）

现有 `session.device_phone_id` / `device_glasses_id`（`models.py:415`）已具备字段，本次只需
确保会话创建时正确写入 `device_phone_id = 初始化 device_id`。`session` 不做结构改动。

## 6. 注意事项与边界情况

### 6.1 SN 校验与防呆

- 服务端：`trim + UPPERCASE` 后只接受 `4–64` 位 `[A-Z0-9._-]`（与现有 mock 规则一致）。
- APP 端录入防呆：过滤非法字符、自动去空格、转大写、限制长度；提供「SN 在哪看」引导
  （手机设置 → 关于手机 → 状态信息 → 序列号）。

### 6.2 并发与幂等

- 同一 `phone_sn` 并发初始化：依赖 `phone_sn` 唯一索引 + upsert（`ON CONFLICT`）保证不重复
  创建；事务内先查后写，命中即更新。
- 同一 `glasses_mac` 被并发初始化到不同手机：最后提交者生效（覆盖语义），无锁冲突。

### 6.3 SN 敏感性与安全

- SN 只允许 HTTPS 上传；不得写入普通业务日志；操作日志记录时脱敏（建议只留后 4 位，如
  `****1234`，或在 `request_params` 中省略 SN 仅记录 `device_id + venue_id + glasses_mac`）。
- 上报/重置接口鉴权后仍建议对 `report` 做简单限流（如按 `phone_sn` 每分钟 N 次），防伪造
  刷库 / 枚举设备资产。

### 6.4 Token 与登录态

- 共用运营账号 + 24h JWT。APP 加密缓存 token；初始化/重置流程中遇 401 → 清除 token →
  引导重新登录 → 登录后回到原动作（不丢失已填的 SN / 场馆等中间状态）。
- 运营账号被停用（`status != active`）时，中间件返回 401 + `code=10207`，APP 应提示账号不可用。

### 6.5 离线 / 网络异常

- 初始化必须联网（`report` 是网络请求）。断网 → 提示网络错误，允许重试；未收到成功响应前
  不落本地 `device_id`。
- 已初始化设备打开直接进使用页，依赖本地缓存的 `device_id`，不强制握手（与旧版
  `handshake` 设计不同）。

### 6.6 重置边界

- 重置仅解除绑定、保留设备记录与累计数据；重置不删除 `device` 行。
- 重置后 APP 本地清空 `device_id` → 回到初始化向导（token 未过期可免登录）。
- 若手机设备存在**进行中的导览会话**（`session.status='active'` 且 `device_phone_id` 指向该
  设备），重置返回 409 并拒绝，需先结束会话再重置；同理报告接口的眼镜换绑覆盖前也需校验旧
  手机无进行中会话（见 §4.3）。

## 7. APP 端实现细节

> 供 APP 同事落地；后端同事了解 APP 侧行为即可。

### 7.1 启动分支

- Launcher 入口判断：本地 `ProvisioningStore` 已存在 `device_id` → 进使用页
  （`MainActivity`）；否则 → `LoginActivity`。

### 7.2 页面结构

- `LoginActivity`：Logo + 用户名 + 密码 + 登录按钮；调 `/v1/admin/auth/login`；成功存
  `OperatorSessionStore` → 进初始化向导。登录失败展示服务端文案与锁定剩余秒数。
- 初始化向导（改造现有 `ProvisioningActivity`，分步骤）：
  - Step1 连眼镜：复用 `BleService` 扫描（15s 超时），强制已连接，取 MAC。
  - Step2 录 SN：防呆输入（见 §6.1）。
  - Step3 选场馆：`GET /v1/admin/venues`（带 token），仅展示 `status=active`，`id/code/name/address`。
  - Step4 确认初始化：`POST /v1/admin/devices/report`（带 token）→ 成功存 `device_id` → 进使用页。
- 使用页（`MainActivity`）：
  - 长按标题/Logo 3 秒 → 运营入口：token 未过期免登录，否则弹登录 → 重置确认弹窗 →
    `POST /v1/admin/devices/{device_id}/reset` → 成功清本地 → 直接进初始化向导。
  - 连点标题 5 次（800ms 窗口内）→ 仅 debug 包开启调试预览：对话/导出页免导览会话直接进入。
  - 创建导览会话时传 `ProvisioningStore.deviceId`（替换原来的 `ANDROID_ID`）。

### 7.3 本地存储

- `ProvisioningStore`（EncryptedSharedPreferences，精简字段）：
  `device_id / phone_sn / glasses_mac / glasses_name / venue_id / venue_code / venue_name /
  venue_address / provisioned_at`。`isInitialized()` = `device_id` 非空。
  **移除**：`install_id`、`device_credential`、`config_version` 等旧字段。
- `OperatorSessionStore`（新建，EncryptedSharedPreferences）：
  `operator_token / expires_at / display_name`。游客模式不读取。

### 7.4 网络层与 Mock 兜底

- 新增 `RemoteProvisioningApi`（真实调用 `/v1/admin/auth/login`、`/v1/admin/venues`、
  `/v1/admin/devices/report`、`/v1/admin/devices/{id}/reset`），通过 `ProvisioningApiProvider`
  单点切换。
- 保留 `MockProvisioningApi` 作为无后端联调 UI 的兜底，用开关切换；Mock 字段与真实接口契约
  对齐（含 `phone_sn → device_id` 复用语义）。

## 8. 现状盘点与待后端对齐点

| 现状 | 结论 |
|---|---|
| 中间件白名单含 `/v1/admin/devices/report`（无鉴权假接口） | **本次改为需鉴权**，移除白名单 |
| `Device` 表缺 `phone_sn / os_version / app_version / name / connected_phone_id` | **新增字段** + `phone_sn` 唯一索引 |
| 无重置接口 | **新增** `POST /v1/admin/devices/{device_id}/reset` |
| `/v1/admin/auth/login`、`GET /v1/admin/venues` | 复用，不动 |
| `session.usage_count` 无人累加；APP 调 `/sessions`（后端不存在） | 会话创建时按 `device_phone_id` 累加；会话接口统一为 `/v1/rentals/start` 或新增（**待后端定**） |
| 旧文档的 `install_id / credential / handshake / provisioning_token` | **全部废弃**，以本文档为准 |

## 9. 后端验收用例

1. 未登录调用 `/v1/admin/devices/report`、`reset` 返回 401。
2. 登录后用同一 `phone_sn` 初始化两次，返回同一 `device_id`，且不产生重复设备记录。
3. 同一 `phone_sn` 改变 `venue_id` / `glasses_mac` 后初始化，`device_id` 不变，绑定更新。
4. 眼镜 `connected_phone_id` 与手机 `connected_glasses_sn` 双向一致。
5. 重置后手机/眼镜的 `venue_id` 与互绑清空，`device_id / phone_sn / usage_count` 保留。
6. 重置后按同一 `phone_sn` 重新初始化，恢复同一 `device_id`。
7. 每次初始化/重置均有 `admin_operation_log` 记录，`request_params` 中无明文 SN。
8. 会话创建后，手机设备 `usage_count +1`。
